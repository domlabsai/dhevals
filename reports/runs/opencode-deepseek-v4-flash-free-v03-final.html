## Causa

O `runJob` em `worker-timeout/worker.mjs` só "detectava" o timeout se **duas coisas assíncronas e frágeis** cooperassem:

1. O `fetchFn` precisava propagar o `signal` e rejeitar rapidamente com `AbortError` quando o timer disparasse. Se o upstream **engole o abort** (resolve depois do deadline), o `await fetchFn` nunca rejeita → o job retorna `{ ok: true }` **após exceder o orçamento em 2,5x** (e se nunca resolvesse, penduraria para sempre — `finally` só roda quando a promise settle).
2. O `catch` decidia o timeout lendo `controller.signal.aborted`, que é estado externo/assíncrono — se um erro real coincidisse com o abort em voo, ele era **mascarado como `TimeoutError`**.

Resultado: o contrato `TIMEOUT_MS` era apenas *advisory* — o timeout disparava **intermitentemente**, dependendo do timing e da implementação do upstream. O timer nunca era consultado no caminho de sucesso.

## Diff mínimo (worker.mjs)

-  const timer = setTimeout(() => controller.abort(), TIMEOUT_MS);
+  let timedOut = false;
+  const timer = setTimeout(() => {
+    timedOut = true;
+    controller.abort();
+  }, TIMEOUT_MS);
   try {
     const res = await fetchFn({ signal: controller.signal });
     clearTimeout(timer);
+    if (timedOut) throw new TimeoutError(`job exceeded ${TIMEOUT_MS}ms`);
     return await res.json();
   } catch (err) {
-    if (controller.signal.aborted) {

- CONTEXTO DO CLIENTE: [objetivo, tom, público, restrições]
- FONTES DE VERDADE: [docs, URLs, dados, políticas, referências]

## Processo de auditoria
1. Leia a entrega inteira antes de julgar.
2. Para cada afirmação factual, cruze com as fontes de verdade.
   Cite a fonte. Se não houver fonte, marque como NÃO VERIFICADO
   (erro factual por ausência de evidência).
3. Confira se a entrega usa o contexto do cliente de forma correta
   (tom, escopo, dados do cliente).
4. Verifique aderência ao critério de aprovação item por item.
5. Classifique cada achado. Nunca misture tipos.

## Classificação de achados
- ERRO FACTUAL: afirmação incorreta, desatualizada ou sem fonte
  verificável. É bloqueante até correção.
- LACUNA DE CONTEXTO: omissão ou uso errado de informação que o
  cliente espera (escopo, público, tom, histórico). É bloqueante
  quando muda o significado ou quebra expectativa.
- MELHORIA OPCIONAL: sugestão válida que não afeta correção nem
  expectativa. Não bloqueia; registre separadamente.

## Severidade
- BLOQUEADOR: cliente perderia dinheiro, credibilidade ou estaria
  exposto a risco legal/operacional.
- ALTO: entrega enganosa ou incompleta no essencial, exige
  correção antes do envio.
- MÉDIO: prejudica clareza ou confiança, corrigível sem reescrever.
- BAIXO: polimento, não afeta a decisão do cliente.

## Regras de auditoria
- Todo achado tem evidência: citação, fonte, trecho ou ausência
  verificável. Sem evidência, o achado não existe.
- Não "seja justo" — seja verificável. Não elogie sem evidência.
- Separe política (não negociável) de preferência (soft).
- Se o critério de aprovação não permitir verificação, diga
  explicitamente e trate como lacuna do processo, não da entrega.

## Plano: Alteração em massa de cadastros (catálogos em `public/data/*.json`)

Alvo típico: `dataset-catalog.json`, `experiment-catalog.json`, `model-catalog.json`, `suite-catalog.json` — todos gerados por `scripts/build-*.mjs`, com campos `id`, `status`, `generated_at`, `content_hash` (já presentes no schema), o que facilita a estratégia abaixo. Nenhuma alteração foi executada; segue apenas o desenho.

### 0. Pré-condições
- Freeze de escrita nos catálogos-alvo (impedir corrida com `build-*` em execução).
- Definir a transformação como **função pura** `T(entry) -> entry` + `rule_version` (semântica versionada, ex.: `migration-2026-08-03.rules-v1`).

### 1. Dry-run (somente leitura)
- Roda `T` sobre cada entrada **sem gravar**; emite `diff` campo-a-campo (antes/depois) por registro.
- Gera relatório: total afetado, entradas válidas/inválidas/sem mudança, e **checksum agregado** (SHA-256 do diff).
- Critérios de parada: qualquer entrada inválida ou > X% de divergência aborta.

### 2. Amostra
- Seleciona amostra representativa (estratos por `status`/`source_type`/`locale`, ex. 5–10 registros, incl. 1 com mudança máxima).
- Aplica `T` na amostra em ambiente isolado (`git worktree` ou ramo `chore/bulk-change`) e gera diff legível para revisão humana.

### 3. Aprovação explícita
- Artefato de aprovação assinado: `{rule_version, diff_sha256, amostra_sha256, approved_by, approved_at}`.
- A execução **não inicia sem** esse artefato; o pipeline valida os hashes antes de escrever.

### 4. Execução idempotente
- Cada aplicação é chaveada por `(id, rule_version, input_hash)`: registrar em `bulk-migration-state.json`. Se já consta aplicado → **skip** (no-op em re-execução).
- Lote com **checkpoint por registro** e resume a partir do último idempotente; falha não deixa estado intermediário inconsistente.

### 5. Trilha de auditoria
- `bulk-migration-audit.json`: por registro `{id, rule_version, input_hash, output_hash, status, applied_at, applied_by, run_id}` + manifest global com hashes antes/depois dos arquivos.

### 6. Rollback
- **Snapshot** dos arquivos originais antes do primeiro write (`backup/` + hash).
- Inversa `T⁻¹` validada em dry-run; reverter = restaurar snapshot e re-rodar builds; marcado como `rolled_back_at` na auditoria.

### Fluxo de portas (gates)
`dry-run → amostra → aprovação → execução → auditoria` — cada gate só abre após o anterior passar e gerar artefato verificável.
