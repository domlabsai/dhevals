## Causa (raiz)

**FATO** (do pacote): `Promise.race` rejeita com o primeiro settle, mas **não cancela** a outra promessa. Quando `timeout(5000)` vence, o fetch continua vivo. Como a exceção interrompe o fluxo antes do `ack`, o job é reenfileirado e uma **segunda** requisição é disparada enquanto a primeira segue ativa.

**INFERÊNCIA:** o "timeout intermitente" observado em produção provavelmente é efeito dessa duplicação (sockets/in-flight em dobro, backpressure), e não latência real do upstream. Não é provável que seja outra causa, mas não há evidência que a prove — o pacote só contém o snippet.

## Diff mínimo

Mantém o fluxo idêntico no caminho feliz e no de erro; a mudança é: criar um `AbortController`, abortar em 5s e propagar o `signal` ao `fetch` (comportamento ativo só via flag).

```ts
export async function processJob(id, deps) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), 5000);
  try {
    const result = await Promise.race([
      deps.client.fetch(id, deps.flags?.abortFetch ? { signal: controller.signal } : {}),
      timeout(5000),
    ]);
    await deps.queue.ack(id);
    return result;
  } finally {
    clearTimeout(timer);
  }
}
```

- Compatibilidade de retorno preservada: no sucesso, `ack` + retorna `result` (mesmo tipo de antes).
- Quando a flag está **off**, o segundo argumento é `{}` (sem `signal`) e o `abort` no timer é um no-op → comportamento idêntico ao original.
- **INFERÊNCIA:** em 5s o timer de abort dispara antes do `timeout` rejeitar (registrado primeiro); logo o `race` rejeitará com `AbortError` do fetch em vez do erro do `timeout`. O retorno é compatível (ainda rejeita), mas **se o contrato exige o tipo/mensagem exata do erro do `timeout`, isso pode mudar — não informado**.

## 1. Risco

A string SQL concatena diretamente `tenantId`, `status` e `limit` vindos do usuário via interpolação `${...}`. **Risco principal: SQL injection de primeira ordem** — um payload em qualquer um dos três campos pode alterar a estrutura da query. Efeitos concretos possíveis:

- `status = "active' OR 1=1 --"` → derruba o filtro de status e pode **ampliar indevidamente o conjunto de linhas retornado**.
- `tenant_id = "1 OR 1=1"` → quebra o **isolamento entre tenants**, expondo `id`/`email` de clientes de outros locatários (fuga de dados).
