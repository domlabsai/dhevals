A busca híbrida parece oferecer melhor cobertura para consultas corporativas com termos exatos e restrições estruturadas. Isso sugere menor risco de não recuperar o documento correto, mas não prova que a resposta gerada será factual ou estará devidamente fundamentada.

Correção mínima: criar um `AbortController`, passar o sinal ao cliente e abortar quando a `race` rejeitar. O erro original do timeout continua sendo propagado.

```ts
// process-job.ts
export async function processJob(id: string, deps: Deps) {
  const controller = new AbortController();

  const result = await Promise.race([
    deps.client.fetch(id, controller.signal),
    timeout(5_000),
  ]).catch((error) => {
    controller.abort();
    throw error;
  });

  await deps.queue.ack(id);
  return result;
}
```

O `catch` aborta somente quando a operação falha — inclusive por timeout — evitando abortar uma requisição que já terminou. O trade-off é que o cliente HTTP precisa respeitar `AbortSignal`; caso contrário, o sinal será marcado como abortado, mas a requisição subjacente poderá continuar.

Teste de regressão com Vitest:

```ts
// process-job.test.ts
import { afterEach, describe, expect, it, vi } from "vitest";
import { processJob } from "./process-job";

describe("processJob", () => {
  afterEach(() => vi.useRealTimers());

  it("aborta o sinal após 5 segundos", async () => {
    vi.useFakeTimers();

    let signal!: AbortSignal;

    const fetch = vi.fn((_id: string, receivedSignal: AbortSignal) => {
      signal = receivedSignal;
      return new Promise<never>(() => {});
    });

    const ack = vi.fn(async () => {});

    const job = processJob("job-1", {
      client: { fetch },
      queue: { ack },
    });

    await vi.advanceTimersByTimeAsync(4_999);
    expect(signal.aborted).toBe(false);

    await vi.advanceTimersByTimeAsync(1);
    expect(signal.aborted).toBe(true);

    await expect(job).rejects.toThrow();
    expect(ack).not.toHaveBeenCalled();
  });
});
```
