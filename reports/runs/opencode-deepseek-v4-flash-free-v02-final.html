**Diagnóstico**

- **tipo de caso**: refatoracao (prompt existente, contrato de saída frágil).
- **Lacunas principais**:
  1. **Contrato sub-especificado** — `versao_a`/`versao_b` não dizem se são o texto bruto ou um id; `mudancas`, `conflitos` e `rastreabilidade` não têm tipo nem estrutura definida. Qualquer modelo vai escolher um formato próprio.
  2. **Ambiguação de classificação** — "mudança de prazo" também é literalmente uma mudança de texto. Sem uma taxonomia do tipo do campo afetado (prazo, escopo, responsável, recurso), o agente não sabe como classificar: ele precisa detectar *qual campo mudou*, não só *que mudou*.
  3. **"Conflito não resolvido" sem definição operável** — para distinguir conflito resolvido de não resolvido, o agente precisa de um marcador no dado (status, campo `resolvido`, versão vigente). O prompt exige uma capacidade que os inputs não fornecem. Instrução não adiciona capacidade (regra 2).
  4. **"Retorne somente JSON válido" é instrução, não garantia** — garantir JSON válido é trabalho de validação (parser/schema), não de redação.
  5. **Rastreabilidade alucinada** — sem âncoras estáveis (seção/ID), o modelo inventa números de linha. Precisa de diff determinístico ou de IDs vindos do próprio documento.
  6. **Edge cases ausentes**: versões idênticas, campo presente só numa versão, mudança só de formatação, reordenação de seções.

**Arquitetura recomendada**

- Prompt único **+ contrato de saída obrigatório** (schema JSON). A tarefa é determinística demais para textão livre.
- Melhor ainda: **`generate -> validate -> repair`** — o passo de validação usa um parser de JSON/schema, não o modelo; o repair corrige só violações listadas.
- Capacidade real que instrução não resolve: **rastreabilidade**. Recomende um tool/etapa de diff por âncora de seção (`secao_id`) ou exigir que os briefs já tragam IDs estáveis.

## Causa

O cronômetro de `setTimeout` roda durante **fetch + `res.json()`** (leitura do corpo). O timeout dispara `controller.abort()` por relógio de parede, sem saber se a resposta já chegou. Com latência variável: os headers chegam dentro do orçamento (ex.: 5ms), mas a leitura/parse do corpo cruza os 50ms; o abort então rejeita o `res.json()` em voo com `AbortError` e o `catch` (worker.mjs:13) reclassifica como `TimeoutError`. Como depende de timing de microtask/jitter do event loop, a mesma chamada ora passa, ora estoura — o sintoma "intermitente". O bug é um falso positivo: a resposta completou, mas foi descartada.
